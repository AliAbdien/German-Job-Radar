# German-Job-Radar

A personal job-search tool, not a toy demo: pull real German AI/ML job
postings from the official Bundesagentur für Arbeit API, extract structured
data from the raw text (title, seniority, skills, salary, location, language
requirements, visa sponsorship) with a small LoRA-fine-tuned local model, and
score each posting against my own profile.

Same local-first pattern as my other projects - the extraction model runs on
my own GPU, not a cloud LLM API called per-posting. That's not just a
privacy point here, it's a real cost/latency one: running hundreds of
postings a day through a big hosted model's API adds up in a way that a
fine-tuned 1.5B-parameter model running locally does not.

## Why this project

I've been job hunting for months. Reading every posting manually to check
whether it's actually a fit (right seniority, right skills, right location,
does it want native German I don't have) is real time I'd rather spend
building. [AI-Portfolio-Agent](../AI-Portfolio-Agent) represents me *to*
recruiters; this finds the postings worth reaching out *for*.

## Why fine-tune a small model instead of just calling a big one

A raw postings feed is genuinely messy - formal corporate German, casual
startup Denglisch, salary present maybe a third of the time, seniority that's
implied by the requirements rather than stated in the title. A big hosted
model handles that easily with a good prompt; the question is whether a
much smaller model, fine-tuned specifically on this one task, can get close
enough to be worth running for free, locally, indefinitely, instead of
paying per-call. That comparison - base 1.5B model vs. the same model after
LoRA fine-tuning - is the actual point of this repo, evaluated honestly in
`src/eval.py`, not asserted.

## How it works

```
Bundesagentur für Arbeit Jobsuche API (official, public, free)
        │  scripts/collect_postings.py
        ▼
Raw posting text
        │
        ▼
src/infer.py  ──►  base or LoRA-fine-tuned Qwen2.5-1.5B-Instruct,
        │           running locally, no API call
        ▼
Structured JSON (src/schema.py: title, seniority, skills,
salary, location, remote policy, languages, visa sponsorship)
        │
        ▼
src/profile_match.py  ──►  weighted score against my own profile
        │                   (skills / seniority / language / location)
        ▼
Ranked list of postings actually worth reading
```

## The training data - and why it isn't scraped postings

Redistributing scraped job-ad text in a public training-data file is a real
copyright/ToS problem for most job boards, even when the *code* around it is
open source. So this repo's training set (`data/seed_postings.jsonl`, 27
examples, generated by `data/seed_postings.py`) is hand-written to be
*representative* of real German postings without being a copy of any real
one: formal corporate German, startup Denglisch, salary present about a
third of the time (matching how often real postings actually state it),
seniority that's sometimes explicit and sometimes only inferrable, a mix of
remote/hybrid/onsite, and - deliberately - a handful of postings with no
ML/AI relevance at all (sales, electrician, sysadmin), so the model has to
learn genuine field extraction rather than "is this an AI job → fill in
plausible-sounding AI fields."

Real, currently-live postings only enter the project at *evaluation* time -
pulled fresh via `scripts/collect_postings.py` from the official API,
never stored or redistributed as training data.

**27 examples is a seed, not a finished dataset.** It's enough to prove the
whole pipeline works end-to-end (which it does - see below), not enough
for the fine-tuned model to be reliably better than the base model yet.
Growing this set (more hand-written examples, or a teacher-model-generated
batch reviewed before adding) is the natural next step before this becomes
something to actually rely on daily - see Limitations.

## Results: base model vs. fine-tuned

Trained for real on an RTX 3080 (10GB), 3 epochs over the 22-example training
split, ~2 minutes end to end. Training loss dropped from 0.84 to 0.10 over
the run (`train_loss` 0.398 averaged). Evaluated both the base model and the
LoRA adapter on the same 5 held-out eval examples, same prompt, same decoding
settings (greedy, `max_new_tokens=400`):

| | Base model (zero-shot) | Fine-tuned (LoRA) |
|---|---|---|
| Parse success rate | **0 / 5 (0%)** | **4 / 5 (80%)** |
| `job_title` / `company` / `seniority` / `remote_policy` / `visa` match | - (nothing parsed) | 1.0 on all, of the 4 parsed |
| `salary.stated` exact | - | 1.0 |
| `salary.min_eur` / `max_eur` exact | - | 0.75 / 0.75 |
| `location` match | - | 0.5 |
| `required_skills` F1 | - | 0.688 |
| `nice_to_have_skills` F1 | - | 0.85 |
| `required_languages` F1 | - | 0.5 |

The headline finding: the base model, given the exact same schema-in-prompt
instructions, couldn't produce output this eval could even parse as valid
JSON on *any* of the 5 examples - it wandered past the JSON object and kept
generating. The fine-tuned model parsed cleanly on 4/5 and got every
categorical field right on those four; the one parse failure was a Pydantic
validation error (missing `salary.stated`), not a JSON-syntax error, i.e.
even the failure mode got more specific after fine-tuning.

**Read this result at the right scale.** 5 eval examples is a tiny sample -
this demonstrates that 22 hand-written examples are enough for LoRA to teach
a 1.5B model *the output format and field discipline* this task needs, not
that the model is production-ready. It answers "does fine-tuning help at
all here" (clearly yes) rather than "how accurate is this in general" (needs
a much bigger eval set to claim).

## What's actually verified

Built in a sandboxed environment with no GPU and no access to Hugging Face or
the Bundesagentur für Arbeit API - so the schema, dataset, and scoring logic
were verified there, and the GPU-dependent pieces (training, live API) were
verified for real afterward, by me, on my own machine:

- **`src/schema.py`** - the extraction schema, validated.
- **`data/seed_postings.py`** - all 27 hand-written examples validate against
  the schema (`python -m data.seed_postings` re-checks this on every run).
- **`src/dataset.py`** - builds the train/eval split and the exact prompt
  format training and inference both use. Verified: 22 train / 5 eval,
  no overlap between splits.
- **`src/eval.py`**'s scoring logic (field-level match/F1) - 9 unit tests,
  including deliberately-broken examples to confirm it actually catches
  mismatches, not just passes on identical input.
- **`src/profile_match.py`** - run for real against all 27 gold labels (not
  model output, the ground truth) as a sanity check: junior AI/ML roles
  (Junior AI Engineer, Junior Data Scientist) score 0.95, completely
  unrelated roles (Vertriebsmitarbeiter, IT-Systemadministrator) score
  0.26-0.40 - a ~4x spread between "worth reading" and "not for me", which
  is what this tool exists to produce.
- **`.github/workflows/ci.yml`** - lint + all 23 tests + dataset build,
  runs on every push without needing torch/transformers/a GPU at all (see
  the CI file's own comment on why - the test suite is deliberately scoped
  to what doesn't need the heavy ML stack).
- **`src/train_lora.py`** - run for real on an RTX 3080, see Results above.
- **`src/jobsuche_client.py`** - the first version (written against the
  documented endpoint shape without being able to reach the API) had two
  real bugs a live run caught: a search path that doesn't exist on the
  current API (`/pc/v4/jobs` - the gateway's 403 for an unmatched route
  reads misleadingly like an auth failure) and a job-details endpoint shape
  that isn't just the search path with a refnr appended (details are a
  separate `pc/v4/jobdetails/{base64-encoded-refnr}` endpoint). Both fixed
  against the current spec at
  [bundesAPI/jobsuche-api](https://github.com/bundesAPI/jobsuche-api) - a
  reminder that "written against the docs" and "actually works" are
  different claims, which is exactly why this section exists.

## Setup

```bash
pip install -r requirements-dev.txt          # schema, dataset, eval-logic, tests - no GPU needed
python -m data.seed_postings                  # validate + regenerate data/seed_postings.jsonl
python -m src.dataset                          # build data/train.jsonl / data/eval.jsonl
pytest tests/ -v                                 # 23 tests, all schema/data/scoring logic
```

On a machine with a CUDA GPU (see AI-Visual-Inspector/SETUP_GUIDE.md for the
`pip install torch --index-url .../cu128` step - `pip install torch` alone
silently gives you a CPU-only wheel):

```bash
pip install -r requirements.txt
python -m src.train_lora --base-model Qwen/Qwen2.5-1.5B-Instruct --epochs 3
python -m src.eval --eval-path data/eval.jsonl                              # base model
python -m src.eval --eval-path data/eval.jsonl --adapter models/lora-adapter  # fine-tuned
```

To pull real live postings and rank them:

```bash
python -m scripts.collect_postings --was "AI Engineer" --n 30 --out data/live_postings.jsonl
python -m src.infer --text "$(cat one_posting.txt)" --adapter models/lora-adapter
python -m src.profile_match --extractions data/extracted.jsonl
```

## Tech stack

- **Base model**: Qwen2.5-1.5B-Instruct (small enough to fine-tune and run
  inference on a 10GB RTX 3080 without quantization)
- **Fine-tuning**: LoRA via `peft` - no 4-bit quantization (unnecessary at
  this model size, and `bitsandbytes`' Windows support has historically
  been unreliable - not worth the risk for a model this small)
- **Data source**: [Bundesagentur für Arbeit Jobsuche API](https://jobsuche.api.bund.dev/) (official, public, free)
- **Schema/validation**: Pydantic
- **Evaluation**: field-level match/F1 against held-out gold labels, base
  vs. fine-tuned comparison

## Design notes

- **Training data is hand-written, not scraped** - the legal/ethical reason
  is above, but it's also just a better dataset: I control exactly which
  kinds of messiness (Denglisch, missing salary, implicit seniority) are
  represented, rather than whatever a scrape happened to catch.
- **Real postings enter only at eval time.** Training on synthetic data and
  evaluating on the real thing is the honest way to answer "does this
  generalize" - training on real (but unredistributable) data and evaluating
  on the same distribution would look better and prove less.
- **The prompt format in training and inference is identical by
  construction** (`src/dataset.py`'s `build_prompt` is imported by both
  `src/infer.py` at inference time and used to build training examples) -
  training on one prompt shape and serving with a different one is a classic,
  avoidable way to tank fine-tuning results without ever finding out why.
- **Evaluation is field-level, not exact-JSON-match.** Two extractions that
  agree on every field but order them differently, or say "ML Engineer" vs
  "Machine Learning Engineer", are not "wrong" - exact-string comparison
  would make the eval numbers meaningless.

## Limitations

- **The eval set is 5 examples.** The base-vs-fine-tuned result above is real
  and measured, not asserted, but 5 examples is enough to show a direction
  (fine-tuning clearly helps on this task), not enough to claim a precise
  accuracy number. Growing both the seed and eval sets is the natural next
  step before trusting this for real filtering decisions.
- **27 seed training examples is small** for LoRA fine-tuning to reliably
  generalize across the full variety of real postings. The current result
  shows the model learned the output *format and field discipline* well -
  whether it generalizes to postings unlike anything in the 22 training
  examples is untested.
- **`profile_match.py`'s scoring is a transparent heuristic**, not learned -
  that's deliberate (see Design notes), but it means the weights (skills 40%,
  seniority 25%, language 20%, location 15%) are a reasonable starting
  point I chose, not something tuned against labeled outcome data I don't
  have (I don't have ground truth on which postings I'd actually get an
  interview for).
- **`src/jobsuche_client.py` had two real endpoint bugs**, found and fixed
  by an actual live run (see "What's actually verified" above) rather than
  by re-reading the docs harder. Worth a fresh live smoke test
  (`python -m src.jobsuche_client`) after any future change to it, since
  government API endpoints have changed shape before without notice.
